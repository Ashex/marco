marco storage engine: no mmap, no page cache

Design and phase plan · written 2026-11-05 · status: proposed, not built

design record (internal)

marco reads its snapshot through mmap. That makes a bad disk read a SIGBUS, a page fault a stalled tokio worker, and the kernel's 4 KiB LRU with readahead the only cache. This doc replaces it with one engine: snapshot pages read with O_DIRECT into memory marco owns, a pinned tier for what every request touches, a scan-resistant page cache under --memory, reads that never block a runtime thread, checksums on every page read from disk, and a checkpoint switch that never goes over the budget. When the budget holds the whole snapshot, everything loads at open and the same code never misses.

1. Open questions

Q1. What --memory covers. The budget caps the snapshot store: pinned tier, page frames and the engine's own tables. Deltas, live DIDs, tombstone maps and the request heap sit on top, because they grow with writes between checkpoints and can't be evicted.
Recommend: store only. Startup warns when --memory is over the cgroup limit less 3 GiB, and the console shows the rest of the RSS next to the budget.
Q2. One bad page. RPCs that touch a page that failed its checksum (or EIO three times) get data_loss (or unavailable) naming file and page. Everything else keeps serving.
Recommend: /readyz stays ready for isolated bad pages and an alert pages, since the fix (rebuild or restore the file) needs a human. Readiness drops only on an EIO storm: 64 distinct pages failing within 60 s, meaning the disk is going.
Q3. Full residency gets about 9% bigger. FORMAT 6 needs about 42.1 GB to hold the whole network in memory, against 38.5 GB of page cache today. The extra comes from page packing, page sums, frame tables and a by-subject index that carries its subjects, so Has on a long list reads one page and not ten.
Recommend: accept it. Under the 48 GiB limit that still leaves about 4.3 GB above a 44 GiB budget for deltas and the process, plus about 5 GB of budget headroom for the checkpoint switch.
Q4. Heat-ordered layout. The builder could lay small lists out by each actor's last write (newest rkey), so active accounts share pages. It's cheap for the builder, but it's a second layout to keep correct.
Recommend: build it as an option in phase 6 and adopt it only if the 8 GiB skewed run shows at least 20% fewer misses.

2. Architecture

The Graph keeps its shape: two copies, deltas in memory, the writer swapping copies. Only Base changes. It reads through a Store whose files live in an engine-wide registry, so the checkpoint's own copy of the graph and the next snapshot share every unchanged file, its pinned parts and its cached pages. Nothing is mapped from a file. The frame arena is anonymous memory with MADV_HUGEPAGE, which takes TLB pressure off the hot path that the 4 KiB page-cache mappings put on it today.

3. FORMAT 6: pages and columns

Three changes do the work. Lists of 128 records or fewer, about 92% of out lists, keep their FORMAT 5 bytes and pack whole into pages, so a small list is one page read. Big lists split into columns. Has, BlockPairs, known followers and filters scan subjects and in sets and never pull in the 13.5 GB of rkeys. Last, everything a lookup needs to find the right block (skips, firsts, offsets, by-subject fences) moves into a pinned head. Every request can then plan the pages it needs from memory and fetch them all in one round.

The by-subject index changes from positions sorted by subject (4 B a record) to blocks of 128 holding the subjects as Elias-Fano, through the in-set block codec, which takes repeats, plus the positions as u32. FORMAT 5 compared subject(bysubj[mid]) at each binary-search step, which on a cold cache is a random subject page per step, about ten dependent reads. The new form costs ~5.6 B a record (4.8 GB against 3.4 GB) and turns the lookup into one page.

Offsets in the index are plain u32 per section, not ascending runs, and lists are self-delimiting. So the order of lists in a section is free, which is what the heat-ordered option (Q4) needs, and the index loses its per-128 base array. FORMAT bumps to 6. There is no reader for 5 and no migration: snapshots are rebuilt from the archive.

5. The cache unit and the policy

UnitLookupMemory overhead at full residencyWaste on a missVerdict
Whole list, any size (object cache)hash map per access~40 B × 66M lists ≈ 2.6 GB, plus allocator fragmentationnoneno: the full-residency case pays the most for it

4 KiB page of one column, blocks never crossing pagesarray index (slots[page])12 B a frame ≈ 0.12 GBsmall lists share a page with ~5 neighbours; big lists waste < 5%chosen

The page wins because the lookup is the same at every budget: index → offset → slots[offset / 4096] → frame. That's one dependent load more than an mmap slice, with no hashing and no per-object allocation. The column split takes care of most of the co-location waste. A page of subjects carries only subjects, and big lists, which hold 82% of records, have pages of their own blocks. The rest is the tail of tiny lists sharing pages, which the heat-ordered option (Q4) targets.

S3-FIFO over W-TinyLFU: it's scan-resistant in the way that matters here, since a page touched once (one big Intersect, a ListIn walk, a cold viewer) dies in the small queue without touching the main one. It's frequency-aware through its 2-bit counters and the ghost. It needs no sketch and no LRU list on hits, only a mutex on the eviction path, which is already a miss costing ~80 µs of disk. Checkpoint, verify and open reads never enter the cache.

Reclamation uses epochs. A request pass pins the epoch (crossbeam-epoch, a few ns) and reads frames as plain slices. The evictor clears a frame's slots, then retires the frame, and reuses it only after every pass that could have seen it has ended. Passes never span an await, so the epoch always advances. Pages a request had to fetch get a pin count until the request ends, so its next pass finds them. Hits take no atomic write.

6. The read path

Find the pages, fetch the misses, compute

Structures stay synchronous and slice-based. What changes is where a slice comes from:

// marco-core
pub struct ReadCx<'g> { guard: epoch::Guard, mode: Mode, missing: PageSet, touched: PageSet, stats: ReadStats }
pub enum Mode { Collect, Block }          // Collect: request path. Block: writer, checkpoint, admin
pub struct Pending;                       // a miss in Collect mode; never returned in Block mode
type R<T> = Result<T, Pending>;

trait Blocks<'g> { fn block(&self, cx: &ReadCx<'g>, b: usize) -> R<&'g [u8]>;
                  fn need(&self, cx: &ReadCx<'g>, bs: Range<usize>) -> R<()>; }   // registers every miss in bs
OutList<'g, B: Blocks> / InList<'g, B: Blocks>    // head from the pinned tier (or the one small-list slice)
impl Graph { fn base_out(&self, cx, rel, id) -> R<Option<OutList>>; fn in_contains(&self, cx, ..) -> R<bool>; ... }

Each structure method first calls need() for every block it will read, which it can work out from the pinned head, and only then decodes. A scan misses all its blocks in one pass, not one per restart. Batch calls (relationships, block_pairs, filter, the probe loops of intersect) catch Pending per item and go on to the next one, so twenty others missing in twenty different lists cost one round, not twenty. In-memory overrides (out_over, in_over) implement Blocks and never miss. The Graph code keeps its logic. It gains cx and a ? at each base access.

// marco-server handler, e.g. relationships
let mut hold = Hold::default();                       // pins on fetched pages, released on drop
for round in 0..MAX_ROUNDS {                          // 6; the table below bounds real requests at 3
    let r = {
        let g = app.graph();                          // Arc, held only for this block
        let mut cx = ReadCx::collect(&app.engine);
        let r = g.relationships(&mut cx, &req.actor, &others, &rels);
        cx.finish(&mut hold)                          // pins everything touched if anything missed
            .map(|()| r)
    };                                                // g and the epoch guard dropped here
    match r {
        Ok(r) => return Ok(build_response(r)),
        Err(missing) => app.engine.fetch(missing, Prio::Request, &mut hold).await
                           .map_err(storage_error)?,  // data_loss / unavailable
    }
}
Err(ConnectError::internal("storage: read did not settle"))

A pass that missed pins every page it touched, hits included, before it drops the guard. Each round therefore strictly grows the resident set the next pass needs, and rounds equal the dependency depth. If a checkpoint switch lands between rounds, the next pass reads the new copy from scratch, and the answer is still computed from one consistent copy. The handler's code runs hidden(), did_of and the rest of the response building inside the final pass, and those use only the pinned tier.

8. Async I/O

Default: a pool of 64 threads doing blocking pread on O_DIRECT fds, fed by two bounded queues (requests first, then writer prefetch and re-warm), with adjacent pages of one file coalesced into one read of up to 256 KiB. It reaches 384k reads/s on this disk at ~3.5 µs of CPU a read. That's 0.35 of a core at 100k misses/s, and it builds and runs everywhere. io_uring (one ring per I/O thread through the io-uring crate, no SQPOLL) would cut the CPU per read to roughly a third and reach deeper queues on one thread. That only pays above ~150k misses/s, and whether the target load gets there is a measurement, not a guess.

9. Writes

An add reads the actor's out list (does the key exist, what did it name) and the subject's in set (is the pair new). A write can't stop halfway through a mutation, so the writer runs a read-only plan pass over the batch that calls the same lookups in Collect mode. It then fetches every missing page in one blocking parallel round on its own OS thread, pinned, and applies in Block mode. A miss the plan didn't predict (a status delete's whole out list, say) blocks only the writer thread, which is allowed. On the Tight case, a cold write costs one I/O round per batch of up to 4,096 records, not one per op. Checkpoint replay (open_replayed) uses the same batching.

10. Checkpoints and the switch

  1. Replay and write. The checkpoint thread's open_replayed gets its files from the registry, the same FileStates the served copies use: no second pinned tier and no second cache. For each dirty shard it streams the old file's paged sections in 1 MiB O_DIRECT reads into two private buffers, checking page sums, and merges them with the deltas. A page none of whose lists changed is copied as-is, and the writer records the run (old page, new page, count). A page with a changed list is re-packed, and the writer records which old pages fed it. Old bytes for changed lists come from the same stream, not the cache. Today's checkpoint rewrote the network in 20-22 s writing 37.7 GB, and the gate is 1.3× that.
  2. Commit. The manifest rename, exactly as now. Decision 63 doesn't change: no WAL, cursors in the manifest, replay after it.
  3. Open the new snapshot. Unchanged files come from the registry. For each new shard file the engine first evicts frames worth its pinned parts (~1.2 GB if every shard is dirty), then loads and checks them. For every copied run, resident frames gain the new file's slot as a second owner (a frame owns at most two slots, and eviction clears both). Copied pages cost no memory and no I/O.
  4. Re-warm. Re-packed pages whose old versions were resident are read back on the low-priority queue into frames, evicting cold ones first. When the budget fits everything (the Fits case), this uses the switch headroom, and if that runs out the coldest pages go. The switch never waits for it, and what it doesn't finish turns into ordinary misses.
  5. Switch. The writer replays the segments after the cut and publishes, as now. When the last Store holding an old shard file drops, its pinned parts free and its frames lose that owner. A frame with no owner left returns to the free list.

The extra memory at the switch is the new files' pinned parts plus the re-warmed pages. Both are taken from the cache, so store memory peaks at --memory, and what varies is how many pages go cold. That's the number E4 measures at 48 GiB, where two copies of a 38.5 GB snapshot can't fit and where today's mmap path lets the kernel evict the served copy's pages to make room for the new files. Over many checkpoints re-packed pages fill unevenly. A shard whose paged sections fall below 85% fill is re-packed whole at its next checkpoint, so copied runs don't decay into half-empty pages.

The skew, and why

AppView reads have two sides, and they're skewed differently. Both weights come from the archive's public records (latest version of each record), exported by an internal script:

  • Viewers (the actor of relationships, known followers, follows pages, filters): DIDs with at least one record created in the 30 days before the snapshot's cut, weighted by distinct active days (1-30). The read mix is per active user, and accounts that write on more days open the app on more days. Lurkers who never write are missed, and the uniform run covers the cold tail.
  • Others and subjects (feed and thread authors, profiles, block-pair authors, known-followers subjects): weighted by likes received in the last 7 days, plus 1 for any DID that posted. An author shows up in hydrations when their posts are shown, and likes are a roughly steady fraction of views, so likes received tracks exposure. Follower count would over-weight big accounts that have gone quiet. It runs as a sensitivity check (--subject-weights followers) at Half only.

Every run reports the share of draws that land on the top 1% and top 10% of weights, and distinct lists touched per minute, so runs are comparable. The public instance's request logs were the other candidate. If an AppView's traffic reaches it, they replace these weights, since they'd be the real thing.

Pass gates

"Meaningfully slower" means more than 5% less throughput, or a p99 more than 10% (and 20 µs) higher at the same offered load. 5% is meant as twice the run-to-run spread. E1's three repeats measure that spread, and if it comes out over 2.5% the gate becomes twice the measured spread, since a gate tighter than the noise can't be passed or failed.

14. Phase plan

Phase 1 · Baseline and skew harness parallel from the start

  • Internal export script: viewer and subject weight files from the archive (section 13), written to internal/raw-storage/.
  • marco-harness perf-inputs --viewer-weights F --subject-weights F: weighted pools next to the existing ones; mix files name them ("actor": "viewer_skew", "subjects": {"pool": "author_skew"}). The report gains top-1%/10% shares and distinct lists per minute.
  • An internal run script: cgroup v2 scopes (systemd-run --user --scope -p MemoryMax= -p MemorySwapMax=0), memory.peak and io.stat collection, cold-cache open via fadvise.
  • E1 on FORMAT 5: Half and Tight right away, Fits after the crawl. Results in internal/raw-storage/.
  • Tests: weighted draws match their weights (chi-square on 1M draws); mix files with the new pools load; the existing harness tests pass.
  • Leaves: the baseline numbers every later gate compares against. No server change.

Phase 2 · Engine core parallel from the start

  • marco-core::store::{page, io, cache, engine}: page sums, the IoBackend trait with DirectPool, Plain and Fault; the frame arena (anonymous, MADV_HUGEPAGE), per-file slot tables, S3-FIFO with ghost, epoch reclamation (crossbeam-epoch), pins, single-flight, two priority queues, coalescing, budget accounting with borrow(); the bad-page set; the file registry; core counters.
  • A PageFile test format (a file of 4 KiB pages with a sums section) so the engine is tested without FORMAT 6.
  • Tests: stress with 32 reader threads plus a tiny budget, every page's content tagged with its id and checked on every read (catches a reused frame); scan resistance (a hot set keeps ≥ 90% hits through a 10× cache-size scan); single-flight (64 concurrent misses on one page → 1 read); budget never exceeded (debug assertion on every allocation); EIO, flipped byte and short read → the right error and a bad page; Plain runs in CI and on the Mac; a criterion bench of the hit path (target ≤ 15 ns per page lookup including the epoch pin per pass).
  • Leaves: a tested library, not wired in.

Phase 3 · FORMAT 6, read over mmap parallel from the start

  • FORMAT 6 writer: small/big split, columns, heads, by-subject blocks (EF subjects + positions), u32 index, page sums, pinned/paged section kinds in the footer. Builder (marco-load build) and write_snapshot produce it.
  • Blocks trait and the block-accessor OutList/InList, with R<T> signatures already in place. The only implementation here is over the mmap, and it never returns Pending, so the Graph's logic changes once.
  • Checkpoint writer for FORMAT 6: dirty shards re-packed page by page, unchanged pages copied, the remap runs emitted (unused until phase 5), whole-shard re-pack below 85% fill.
  • Tests: property tests of the new list codecs against FORMAT 5's on random lists (sizes 1, 8, 9, 127-129, 4,095-4,097, repeats, non-TID keys); every existing marco-core and marco-server test on FORMAT 6; the kill tests (killtest) pass; the whole-network build on the load box against the build gate, and verify clean.
  • Leaves: the server running on FORMAT 6 through mmap, so the format is proven in production shape before the engine reads it.

Phase 4 · Miss-aware read path needs 2 and 3

  • ReadCx (Collect/Block), Pending, per-item catch in batch calls, need() planning in the structures; the handler loop in graph_svc.rs (and the admin console's reads) with Hold pins and MAX_ROUNDS; writer plan-pass prefetch; Block mode for checkpoint replay and admin jobs.
  • --storage mmap|engine (default mmap) and --memory; full-residency load at open; error mapping to data_loss/unavailable; the per-RPC page and round histograms.
