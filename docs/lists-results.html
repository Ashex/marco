Both runs on the load box, the same day: P1's binaries on the P1 snapshot, then this build on the lists snapshot, each the median of three rounds after a warm-up, one thread per latency and 32 for throughput. Most reads match within noise. Two don't: relationships and the block filter are slower here, and the rounds inside each run agree with each other, so it isn't run-to-run jitter. This run can't say why. Relationships asks follow and block only, the snapshots are different builds from different exports (so the sampled actors differ), and the binaries differ in everything that landed since P1, not only lists. Mutuals for the most-followed actors went the other way, 3.3 ms to 1.3 ms. A follow-up that builds the P1 export with this build, or runs these binaries on both snapshots, would separate the causes.

Method

The listitem export is the archive's raw ops (crawl_records as creates, repo_records' creates, updates and deletes) with the list URI as a fourth column; the build keeps the latest op per (repo, rkey) and refuses lists in another repo. Follows and blocks come from the P0 raw export, the same files P1's snapshot was built from. Each latency is the median round (by mean) of three after one warm-up round, one thread, over a snapshot whose pages were touched first; the 20 big lists are the largest by record count among all lists with items, the hot members and followed actors the top 20 of 10,000 sampled. Inputs are drawn once from a fixed seed. Writes run on a second, mutable copy of the graph opened from the same snapshot.
