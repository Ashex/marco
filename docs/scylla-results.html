Scylla had half the box: 16 shards on 8 cores and their SMT siblings, 28 GB of memory. The client had the other 8 cores. A real cluster has more shards per node and more nodes, so its scan runs that many times faster until the client or the network is what's full.

How a rebuild works

scan → spill → build → catch-up. The scan writes the same input any exporter writes; the build doesn't know where it came from.

scan-scylla asks the cluster who owns each token. These tables use vnodes, so each vnode's range is cut where Scylla's sharding function moves to the next shard (212 stripes a node), and every shard's pieces are grouped into 8 ranges: 256 ranges of 65,799 pieces over 2 tables. Each query goes straight to the shard that owns its range, with BYPASS CACHE, CL ONE and LZ4.

Rows land in 1,025 files per relation by the repo DID's first two characters, which is the order the build needs. A checkpoint every 10 s records each file's length and each range's position, so a crash resumes from there. The scan writes the time it began, less 5 minutes, as the snapshot's time_us, and marco serve --jetstream starts there.

Scylla's CPU is the limit. At the default 2 ranges in flight per shard its 16 threads were 92% busy, its reactors 88%. The client used 2.9 of its 16 threads and the NVMe read 484 MB/s of the drive's ~7 GB/s. Twice the ranges in flight bought 5% and 8 bought nothing. One range per shard left shards idle while each waited on its next page (75% busy, 8.8M rows/s).

Each Scylla shard served 0.7M rows/s. On a real cluster the scan scales with total shards until the client runs out: at 2.9 client threads per 11M rows/s, one 32-thread client would carry ~110M rows/s, which is ~8.5 GB/s of row data, several 10 Gb/s links' worth before LZ4. So past a few big nodes the network is the next limit, and LZ4 on the wire is what stretches it.

The last 5% of the ranges took the last ~15 s, finishing one or two at a time. More, smaller ranges per shard would shorten that tail.

The client's peak RSS was 9.0 GB at 2 in flight and 11.5 GB at 8, over the 4 GB --memory-gb budget: the budget counts the chunks, not everything around them (task 963).

fill-scylla wrote the export's current state with CQL: each actor's records in unlogged batches of 32, 2,048 batches in flight, token-aware so each batch went to its owner shard. That loaded all 2.97B rows in 33 min, so SSTable generation wasn't needed and there's no subset to extrapolate from. Scylla was the limit here too (13.9 of 16 threads), and compaction kept up: the flush and the wait for compactions after took 2 s.

On disk that's 118 GB, 40 B a row with Scylla's default LZ4 sstable compression. The export it came from is 73 GB of zstd ops.

Method

ScyllaDB 2026.3.4 in Docker with host networking and its data on the NVMe, developer mode (the filesystem is ext4, which production mode refuses), --smp 16 --memory 28G pinned to CPUs 0-7 and 16-23. fs.aio-max-nr was raised to 4,194,304 for the run and put back to 65,536 after. One keyspace at RF 1 with tablets off, tables ((actor_did), rkey) with text columns. marco-load was the release build of CR 1088 PS4, pinned to CPUs 8-15 and 24-31.

Each scan ran from a cold page cache (drop_caches first) into an empty directory. A sampler recorded Scylla's container CPU from its cgroup, per-shard reactor utilization from Scylla's Prometheus endpoint, the client's CPU and the NVMe's bytes every 5 s. The first end-to-end attempt waited on the admin /metrics endpoint, which needs the admin token, and was rerun. The page is generated by internal/scylla_report.py from internal/raw-scylla/, and internal/run-scylla.sh is the run.

Everything the run made on the box (Scylla's data, the image, spills, snapshots) was deleted after. Docker was already installed and stays.
