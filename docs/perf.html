The setup

Server and client never share a core. Each shape runs against three targets, so the cost of each layer shows: the engine alone, the server's handlers and codec without sockets, and the real server over HTTP/2. In-process runs also go to 24 threads (cores 0–11), with no client to make room for.

Every target runs the same requests: P0's inputs (seed 42), drawn once from the snapshot as DIDs. P0 measured the engine from marco-load bench; this page measures the API as clients see it.

One has costs 684 ns in the engine, 3.3 µs through the handlers and codec in-process, and 38.7 µs over HTTP/2. Serial latency over a socket is mostly the round trip: both sides' HTTP/2 and runtime, two wakeups and the kernel's loopback. The server's own time (the last column, from its marco_rpc_seconds) is a fraction of it. Shapes that return more strings pay more in every layer: relationships 50×2 is 29.8 µs in the engine and 101.9 µs over HTTP/2.

The engine scales with cores and keeps going on second threads: has goes from 1.31M/s on one thread to 24.52M/s on 16 and 33.07M/s on 24, since a point read is a few cache misses and the threads share nothing. Through the server the same has is 74k/s per thread and 1.05M/s on 16: 4% of the engine. The gap is what each request costs outside the graph (the profiles below), and it shrinks as the request does more graph work: relationships 50×2 through the server is 53% of the engine's rate.

The first runs used the generated Connect client on 8 threads, and from 8 server threads up the client was the limit: 97% busy on has with the server at 7.3 of 8 cores. For has, marco's own graph code is 16% of the server's cycles; HTTP/2, the runtime and the kernel take 53%, and Connect, axum and protobuf 30%. Relationships 50×2 turns that around: 71% graph code, of which DID lookup alone is 23% (51 DIDs parsed and found per request) and formatting URIs and DIDs back out 4%. The handlers also copy every request into owned strings before they start (to_owned_message), which shows under protobuf. So for point reads the server is a network server with a small graph inside; making it cheaper means fewer, bigger requests (batching) more than a faster engine.

Every shape holds its rate to within a step of its closed-loop maximum, then falls over: once offered load passes what the server completes, the queue grows for the rest of the step and latency runs to seconds (completed/s in the table stays at the ceiling). For has that ceiling is 956k/s sustained, with the server's 16 threads about 15 cores busy.

The tail below saturation is the surprise. At 265k/s of has (a quarter of the maximum) p50 is 38.7 µs but p99 is 1.56 ms, while marco's own handler time for the same requests is p99 31.8 µs (its marco_rpc_seconds) and the client's dispatch lag p99 124.4 µs. So the millisecond is in HTTP/2 I/O and wake-ups between them, not in the graph. It doesn't move with the client (the generated one gives the same) or the connection count (4 to 64), and it shrinks toward saturation, when every worker is already awake. Task 955 has it.

On the read-only server the mix holds 474k/s at p99 11.73 ms and saturates at 522k/s. Following live Jetstream changes neither: the mix still holds 427k/s. The other way round, reads don't move the source's lag at all (p99 413 ms with no reads, 253 ms at 427k/s, all of it upstream), but they do slow the writer: one apply's p99 goes from 318.2 µs to 4.57 ms once reads keep all 16 server threads busy, since the writer thread competes with them for the same cores.

1,000 synthetic writes a second cost far more than their own work. Alone (with almost no reads) they keep 0.1 server cores busy, but with the mix running they add 2.1 cores at 237k/s of reads, and the mix saturates at 356k/s offered, completing 340k/s instead of holding 356k/s. WriteBatch p99 near that point is 9.76 ms. Each batch publishes a new copy of the graph, and every read after it works on a copy whose deltas aren't empty; P1 saw the same as has's p50 rising from 0.6 to 1.4 µs under ingest. Task 956 follows it up.

From another host

Measured with the read mix (read-mix.html section 7, task 958): the 16-thread server on the load box, the lean client on a second box of the same kind over 2.5 GbE. Closed loop it reached 311k calls/s against 385k from the same host, with the client's link carrying 2.37 of its 2.5 Gbit/s: across this LAN the link, not the server, is the limit. One request at a time the shapes' p50s go from 37–106 µs on the same host to 102–255 µs across the LAN, about 60–150 µs more each. The LAN listener was open for that run only.

TCP_NODELAY (task 951). The listeners didn't set it. An HTTP/2 response that goes out as two writes (headers, then a body past a few hundred bytes) then waits for the client's delayed ACK, about 40 ms. Has and counts fit in one write and never showed it; pages, relationships and filter did, but only with one request on a connection: under load other streams' packets carry the ACK. Fixed in this CR (serve sets it on accept), with a test.

any_status (task 952). Every handler asks whether each DID in the request is hidden (taken down or deleted), and that asked any_status() first, which scanned the snapshot's whole status bitset when no actor has a status: 45.6M bits, about 150 µs. P0 and P1 measured the engine, which doesn't ask, and the test snapshots are too small to show it. Fixed in this CR: the bitset never changes, so it's decided once at open.

Method

  • Box. The P0 and P1 load box: AMD Ryzen AI Max+ 395 (16 cores, 32 threads), 61 GiB of RAM, one NVMe drive, Linux 7.0, idle apart from the run. The snapshot sat in the page cache throughout.
  • Build. Release binaries of marco and marco-harness from this CR: next at CR 1084 plus this CR's two fixes and the harness. jemalloc in both, as the server ships.
  • Snapshot. P1's whole-network snapshot, 2.97B edges, 38.5 GB, 64 shards; read-only for every run but the mix with ingest, which ran on a copy.
  • Inputs. marco-harness perf-inputs draws P0's inputs (seed 42, in P0's order) as DIDs: 10,000 random actors with a follow, a followed subject each (hits) and a random DID (misses), 50 others per actor for relationships (25 it follows), the 20 most-followed and most-following actors, cursors after 1,000 followers, 1,000 pages of 50 for filter. Mutuals on the hot account always uses the 886k-follow one (P0 cycled the top 20).
  • Load generator. marco-harness perf over 16 HTTP/2 connections (h2c), Connect with the proto codec: the generated client for one-at-a-time latency, and for throughput, open loop and the mix a lean mode (--raw) that encodes the request bodies once and sends them on hyper's HTTP/2 directly, reading each response whole and checking its status. Closed loop: N tasks, one request each in flight. Open loop: a sender thread of its own issues requests at a constant rate and each latency runs from the request's intended send time, so a stalled server can't pause the sender and hide its queue. Latencies go into log-linear histograms (64 buckets per power of two, under 1.6% error). Each step has 1–2 s of warm-up that isn't counted.
  • CPU and memory. The server's CPU from /proc/<pid>/stat around each measured window; the client's from getrusage. RSS split from /proc/<pid>/status, page cache and MemAvailable from /proc/meminfo. Profiles from marco's /debug/pprof/profile (pprof-rs at 99 Hz, 10 s under closed-loop load), summarized by go tool pprof -traces.
  • Ingest. The mix with ingest follows live Jetstream (jetstream2.us-east) on a copy of the snapshot; lag and apply time come from marco's own marco_ingest_lag_seconds and marco_ingest_apply_seconds, scraped around each step (power-of-two buckets, interpolated). Synthetic writes are follow adds between random actors, 10 per WriteBatch.
  • Reproduce. internal/run-perf.sh runs each step; internal/perf_report.py collect copies its JSON into internal/raw-perf/ and summarizes the profiles, and internal/perf_report.py writes this page from those and P0's raw/bench.json.
