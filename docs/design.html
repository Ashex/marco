marco

A small, fast graph database for atproto actor-to-actor edges: follows, blocks, and any record whose subject is a DID.

Scoping draft · 2026-11-04 · nothing built

vlDB indexes all of app.bsky, so it's too big for anyone else to run. marco is the piece most appviews actually need on day one: who follows, blocks or otherwise points at whom. It should be a single binary that holds the whole network's graph on one ordinary box, with an add call, a delete-by-URI call, and the read calls an appview hydrates with.

Data model

An edge is a record, not a pair. Its identity is (actor, relation, rkey), so a repeat create is a no-op and a delete removes exactly one record. The pair view, "a follows b", holds while at least one record does. That matters because 0.12% of follow records duplicate one the actor already has.

Storage layout

The out log is the only place rkeys live. Its rkey order is time order, so it gives deletes a binary search, gives getFollows its order and cursor for free, and gives every edge a created-at from the TID. The in set stays an id-sorted set, because membership and intersection speed come from that and vlDB measured Elias-Fano at 2.9 B/edge for follows. Lookups in lists over a few thousand edges by subject get a small per-list subject→position index. That's under 0.1% of actors.

A TID's top bit is always 0, so a non-TID rkey becomes 1 ‖ hash63(rkey) in the same u64 column, and one function at the edge of the API does the mapping. A small side table keeps the strings so URIs come back exact. These sort as newest in lists, which is the one place they behave differently.

API

One ConnectRPC service, defined in protobuf and served by connectrpc + buffa. A Connect server answers three protocols on the same port: gRPC, gRPC-Web, and Connect's own HTTP POST with JSON or binary bodies. So curl with JSON works, hydration paths get protobuf, and every language gets generated clients from one .proto. Ingest is a client stream, so a pipeline pushes ops without a round trip per batch. Every write carries an optional source cursor, so a pipeline can resume and replay without double-applying.

Writes, durability and ingest

One writer thread applies ops in order. That's plenty: follows and blocks together averaged 28 ops/s over the last 30 days, and a bulk load skips it entirely. The server keeps two copies of the graph's in-memory part (the snapshot is shared); the writer applies a batch to one, publishes it, and applies the same batch to the other once its readers have left. A write is applied and visible when it returns.

There's no write-ahead log. Every source marco ingests is replayable from a cursor, and replaying an ordered suffix is idempotent because edges are keyed by URI, so a log would be a second copy of data upstream already keeps. Every few seconds the ops applied since the last cut go to a change segment with every source's cursor at that cut, written whole (temp file, fsync, rename), so there's no torn tail. A kill loses at most those seconds, and the sources replay them. The tradeoff: a restart needs the source reachable and within its retention. A source's first cursor and the operator's statuses are written at once, and a WAL can come back if an API writer ever needs ack-durability.

A snapshot is a set of shard files, one per id range (64 to start), named by a manifest along with the cut's cursors and the last segment folded in. Every op dirties two random shards, so rewriting dirty shards often would rewrite all of them (31 GB for 0.1% of the graph). Rewrites only pay off when rare, and the segments are what make rare rewrites safe: a checkpoint runs when replaying the segments would take about 10 s (3M ops) or daily, takes one consistent cut, rewrites the shards that changed (lists without changes copy byte for byte), and renames the manifest, which is the commit. Restart is mmap the shards, replay the segments after the cut, and serve once every configured source is caught up.
