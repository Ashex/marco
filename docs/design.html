marco

A small, fast graph database for atproto actor-to-actor edges: follows, blocks, and any record whose subject is a DID.

Scoping draft · 2026-11-04 · nothing built

vlDB indexes all of app.bsky, so it's too big for anyone else to run. marco is the piece most appviews actually need on day one: who follows, blocks or otherwise points at whom. It should be a single binary that holds the whole network's graph on one ordinary box, with an add call, a delete-by-URI call, and the read calls an appview hydrates with.

Data model

An edge is a record, not a pair. Its identity is (actor, relation, rkey), so a repeat create is a no-op and a delete removes exactly one record. The pair view, "a follows b", holds while at least one record does. That matters because 0.12% of follow records duplicate one the actor already has.

Storage layout

The out log is the only place rkeys live. Its rkey order is time order, so it gives deletes a binary search, gives getFollows its order and cursor for free, and gives every edge a created-at from the TID. The in set stays an id-sorted set, because membership and intersection speed come from that and vlDB measured Elias-Fano at 2.9 B/edge for follows. Lookups in lists over a few thousand edges by subject get a small per-list subject→position index. That's under 0.1% of actors.

A list is a node

A listitem is three ids, not two: owner, list and member. The list gets an id in the directory, keyed by its AT URI, so the list → member edge reuses the out log and the in set unchanged. A delete only names the owner and the rkey, so a companion relation, listitem.owner, keeps the record itself: owner and rkey to list. That's the per-(owner, rkey) map, in the out-log format that already does tombstones, non-TID rkeys and deleted accounts. Every listitem must name a list in its own repo, as the appview requires. The 43k that don't are refused.

The owner log costs ~8 B per edge, ~500 MB at today's size, about 1.5% of the graph. It keeps deletes inside the P0 delete target for every owner and gives the record one identity for tombstones. Membership of x in L is a probe of x's own in set, which is short (p99 78 lists), and materializing a list's members reads its out log: a gather through the by-subject index for the 829 big lists, a sort of at most 4,096 for the rest.

Sets and operations

A list is just another (rel, dir, node) side, so Intersect takes it as is and gains a difference. The one new trick is the identity at the bottom right: any out set can be probed through its members' in sets, so a small side against a huge list never decodes the list. Filter gains a drop rule for "in this set", which is how a feed drops a list's members.

Ingest, build and durability

Jetstream and the firehose read the list path from the record next to the subject, and an add op carries it (AddOp.list, segment op 3). The bulk build reads listitem chunks with a fourth string column, the list URI, after the subject. It resolves each (owner, rkey) to its latest op, as for every relation, then writes the record twice: by owner into the owner log and by list into the list log. Since a list's URI starts with its owner's DID, a repo-prefix chunk's lists are a contiguous id range too, so the out pass places them the same way. Deletes, tombstones, deleted accounts and change segments all go through the owner log, so the durability tests run unchanged with listitems mixed in.

An update can move a listitem to another list, or a follow to another subject, under the same rkey. An add of a key that holds something else replaces the record in every structure, and a create or update that isn't an edge (a list in another repo, a subject that isn't a DID) empties the key like a delete. Applied in order, a source's ops end where the bulk build's latest op per key does.

Two sources overlap: a backfill, or a rebuild's catch-up, hands over ops the live tail already passed. So each key keeps a stamp, the time and source of its last change. From another source, an add older than it changes nothing, and so does a delete of a record changed after the delete. The stamp's own source always applies, in arrival order: 2.3% of deletes land within a second of their create, so a clock that steps back, or a switch between Jetstream and the firehose, would otherwise strand a source's own deletes. An account's deletion takes every record, stamped or not. A plain create's stamp lives in memory until the next checkpoint. A key that was replaced, or re-created after a delete, keeps its stamp in the snapshot beside the tombstones, with their TTL, since no source replays further back. Records never replaced carry nothing, so the cost is about zero.

A firehose frame whose record block is missing or unreadable is skipped, not mapped to a delete. It says nothing about the new record: a delete would drop a good record whenever a relay elides a block, and a rebuild would keep it. These are counted (missing_block, bad_record), and the next update or the next rebuild settles the key.

API

One ConnectRPC service, defined in protobuf and served by connectrpc + buffa. A Connect server answers three protocols on the same port: gRPC, gRPC-Web, and Connect's own HTTP POST with JSON or binary bodies. So curl with JSON works, hydration paths get protobuf, and every language gets generated clients from one .proto. Ingest is a client stream, so a pipeline pushes ops without a round trip per batch. Every write carries an optional source cursor, so a pipeline can resume and replay without double-applying.

Block pairs

Every post the AppView hydrates checks blocks between its author and the parent's, root's and quoted post's authors, all of a response's pairs in one getBlockExistence. Relationships answers one actor against many others, so the read mix had to split those pairs by first actor: 2.4 pairs a call, and the call's fixed cost was most of the price. BlockPairs takes the response's pairs as they are.

Known followers' total

A profile shows "followed by A, B and N others": five DIDs and the size of the viewer's follows ∩ the subject's followers. Intersect paged the ids and returned each side's length, so the total meant paging through all of it. Now count asks for it: total is exact up to count_limit (default 1000, at most 10,000) and total_capped says there's more. The page doesn't change, and nothing is counted unless asked.

The cap matches what the UI does with the number: past a thousand it reads "1,000+". The work is bounded by the side the page already decodes. A typical viewer's few hundred follows are tested against the subject's in set, so the count is a few hundred Elias-Fano lookups. For the 886k-follow account the smaller side is its own follow list, decoded by the by-subject walk that makes mutuals slow. That decode is the page's cost and is left as it is for now. The count adds at most one pass over those members, and stops at the cap. AND_NOT is bounded the same way: b is probed when it's an in set or much bigger than a, and otherwise decoded once and merged with a in one walk, whichever chunk of a the page or the count is on. With a = 886k out follows and b the same accounts less every 600th (b decoded), a page of 5 takes 1.4 ms, the page and a total to 1000 take 2.6 ms, and decoding both sides takes 1.5 ms. Writes, durability and ingest

One writer thread applies ops in order. That's plenty: follows and blocks together averaged 28 ops/s over the last 30 days, and a bulk load skips it entirely. The server keeps two copies of the graph's in-memory part (the snapshot is shared); the writer applies a batch to one, publishes it, and applies the same batch to the other once its readers have left. A write is applied and visible when it returns.

There's no write-ahead log. Every source marco ingests is replayable from a cursor, and replaying an ordered suffix is idempotent because edges are keyed by URI, so a log would be a second copy of data upstream already keeps. Every few seconds the ops applied since the last cut go to a change segment with every source's cursor at that cut, written whole (temp file, fsync, rename), so there's no torn tail. A kill loses at most those seconds, and the sources replay them. The tradeoff: a restart needs the source reachable and within its retention. A source's first cursor and the operator's statuses are written at once, and a WAL can come back if an API writer ever needs ack-durability.

A snapshot is a set of shard files, one per id range (64 to start), named by a manifest along with the cut's cursors and the last segment folded in. Every op dirties two random shards, so rewriting dirty shards often would rewrite all of them (31 GB for 0.1% of the graph). Rewrites only pay off when rare, and the segments are what make rare rewrites safe: a checkpoint runs when replaying the segments would take about 10 s (3M ops) or daily, takes one consistent cut, rewrites the shards that changed (lists without changes copy byte for byte), and renames the manifest, which is the commit. Restart is mmap the shards, replay the segments after the cut, and serve once every configured source is caught up.
